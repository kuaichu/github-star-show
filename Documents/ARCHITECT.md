# 架构文档

这份文档描述 `GitHub Star Show` 当前的系统结构、核心建模思路、同步模型和后续扩展边界。

它与 `README.md` 的区别是：

- `README.md` 讲项目是什么、当前已经能做什么
- `DEPLOYMENT.md` 讲怎么部署、怎么更新
- `ARCHITECT.md` 讲系统为什么这样设计、后面应该沿着什么方向演进

---

## 1. 架构定位

这个项目的底层产品模型不是：

- GitHub Star 的纯镜像
- 通用书签管理器
- AI 驱动的知识库

它的定位是：

> 以 GitHub Stars 作为采集入口，以本地项目库作为长期整理层的混合同步系统。

也就是说：

- GitHub 提供远端事实
- 本地数据库提供用户整理结果

---

## 2. 高层结构

```text
浏览器（Vue + Vite）
        |
        v
后端 API（Express）
        |
        +--> Prisma ORM
        |        |
        |        v
        |      SQLite
        |
        +--> GitHub REST API
        |
        +--> 可选 AI 分类服务
```

### 前端职责

- 登录入口
- 项目浏览
- 分类导航
- 详情抽屉
- 后台编辑
- 筛选、分页、语言切换
- 更新记录展示

前端应保持“轻逻辑、重展示”的原则，不承担同步规则和分类规则的核心判断。

### 后端职责

- GitHub OAuth
- 会话生命周期
- 星标同步
- 分类执行
- 远端状态检查
- 用户与项目持久化
- 数据冲突与覆盖策略

### 数据库职责

- 用户状态持久化
- 项目元数据持久化
- 用户与项目关系持久化
- 同步历史记录
- 未来支持更细粒度的追踪与扩展

---

## 3. 核心领域拆分

当前系统可以自然分成五个领域。

### 3.1 身份域

负责：

- GitHub 登录
- 本地用户创建
- GitHub 账号绑定
- 会话持久化
- 权限边界，例如是否允许代用户取消 Star

### 3.2 仓库目录域

负责：

- 仓库元数据
- 项目列表
- 项目详情
- README 拉取
- 单仓库导入

### 3.3 用户整理域

负责：

- 分类
- 备注
- 推荐标记
- 本地状态
- 自定义标签与高亮

### 3.4 同步域

负责：

- 首次全量同步
- 日常增量同步
- 全量重同步
- 同步记录
- 远端状态校验

### 3.5 分类域

负责：

- 规则分类
- `topics / keyword / language fallback`
- 未来的本地 NLP
- 可选 AI 增强

### 3.6 分类管理域

负责：

- 用户自定义分类的创建、重命名、删除
- 按用户隔离的分类列表
- 首次登录时自动种子化初始分类
- 删除分类时级联归为未分类

## 4. 数据模型设计意图

### `User`

本地应用用户。

### `GithubAccount`

用户绑定的 GitHub 身份，负责保存：

- GitHub 用户 id
- login
- 授权信息
- scope / 能力边界

### `Session`

持久化登录会话。

### `Project`

全局仓库主表，保存 GitHub 仓库的共享事实：

- 仓库名
- 作者
- GitHub 地址
- 描述
- 语言
- topics
- stars 数
- 更新时间
- 最新 Release 时间
- 最新 Commit 时间
- 活动数据检查时间

### `UserProject`

用户与项目的关系表，是当前系统最关键的一张表。

它保存：

- 用户自己的分类
- 备注
- 推荐标记
- 本地状态
- 远端状态
- 同步时间
- 未来的分类来源与分类依据

### `SyncRun`

每一次同步执行的记录表。

保存：

- 同步模式（全量 / 增量）
- 时间
- 数量
- 结果

### `ManagedCategory`

用户自定义分类表，按用户隔离。

保存：

- 分类名称
- 所属用户 id
- 创建时间

设计要点：

- 每个用户首次访问时自动种子化 7 个初始分类（AI / LLM、运维 / 自建服务、网络 / NAS / 虚拟化、媒体 / 下载 / 图床、安全 / CTF、前端 UI / 可视化、自动化 / 效率工具）
- 所有分类均可由用户重命名或删除，无“默认分类不可修改”的限制
- 删除分类时，使用该分类的项目自动移到“未分类/待整理”
- `@@unique([userId, name])` 保证每个用户内分类名称唯一
- `ManagedCategory` 只管理用户可选分类列表（用于后台分类管理和前端分类筛选的下拉选项），不取代 `UserProject.category` 作为项目当前分类结果。项目归类仍由规则分类、AI 或手动编辑写入 `UserProject.category`，`ManagedCategory` 仅提供可选的分类命名空间。

## 5. 为什么同时存在 `Project` 和 `UserProject`

这是当前架构里最重要的设计之一。

### `Project` 存在的原因

- GitHub 仓库元数据本身是全局事实
- 避免同一个仓库在数据库中重复存很多份
- 同步和导入时有统一的仓库基础记录可更新

### `UserProject` 存在的原因

- 不同用户可能收藏同一个仓库
- 但他们的分类、备注、状态完全可能不同
- 用户整理结果不应该互相覆盖

所以：

- `Project` 负责“仓库是什么”
- `UserProject` 负责“这个用户如何整理这个仓库”

这条边界后续应该继续保留，不建议合并。

---

## 6. 同步模型

当前同步模型是多模式的。

### 增量同步

目标：

- 快速拉取新 Star 的项目
- 适合日常频繁使用

特点：

- 更轻
- 更快
- 不做重度校验
- 后台非阻塞刷新新增项目的维护活跃度（Release / Commit 时间）

### 全量同步

目标：

- 与 GitHub 做完整对齐和远端状态校验

特点：

- 更慢
- 更重
- 用于检测：
  - 已取消 Star
  - 已归档
  - 疑似失效
- 后台非阻塞刷新所有项目的维护活跃度（Release / Commit 时间）

### 为什么两者都要保留

- 只有增量同步：长期会变 stale
- 只有全量同步：日常体验会太重

所以当前策略是：

- 日常手动同步走增量
- 周期性或手动修复走全量

---

## 7. 远端状态策略

当前系统不是严格镜像，而是“保留本地资产 + 标记远端状态”。

当前远端状态：

- `active`
- `unstarred`
- `archived`
- `missing`

### 设计原则

当 GitHub 上的状态变化时：

- 系统优先保留本地记录
- 不自动硬删除
- 用状态标签提示用户处理

这样做的原因是：

- 用户可能已经写了备注
- 已经做了分类
- 已经把仓库纳入自己的长期项目库

如果因为远端取消 Star 就直接删除，会破坏这个产品的核心价值。

---

## 8. 手动修改保护策略

后续推荐采用“字段级保护”，而不是“整条记录冻结”。

### 应被保护的用户整理字段

- 分类
- 备注
- 推荐标记
- 本地状态

### 仍然允许同步更新的远端事实字段

- 仓库名
- 描述
- stars 数
- 更新时间
- 远端状态
- 最新 Release 时间
- 最新 Commit 时间
- 活动数据检查时间

### 原因

如果用户只是改了一条备注，就把整条记录彻底冻结，会导致：

- 仓库已经归档了但本地不知道
- 仓库描述更新了但本地不更新
- 同步系统失去可信度

因此推荐：

- 用户整理字段受保护
- 远端事实字段继续同步

---

## 9. 分类架构

分类应该坚持分层设计。

### 第一层：规则分类

这是默认主路径，应优先支持：

1. `topics`
2. `name / description` 关键词
3. `language fallback`
4. `uncategorized`

优点：

- 低成本
- 可解释
- 不依赖 AI

### 第二层：未来本地 NLP

只有在规则系统稳定、样本更干净之后才考虑引入。

角色应是：

- 处理规则没有命中的尾部项目

而不是取代规则系统。

### 第三层：可选 AI

AI 应该保持：

- 可选
- 批处理
- 只处理更难的项目

不应成为系统正常运行的前置依赖。

## 10. 详情流与写入流

### 项目列表流

1. 前端请求当前用户项目列表
2. 后端根据 session 识别用户
3. 后端聚合 `Project + UserProject`
4. 返回统一视图数据
5. 前端做筛选和分页

### 项目详情流

1. 前端请求单个项目详情
2. 后端聚合用户级视图
3. 后端拉取 README
4. 前端展示概览、README、备注、链接

### 本地编辑流

1. 用户在后台修改项目
2. 前端提交 patch/create
3. 后端更新全局项目事实与用户关系层
4. 未来同步逻辑应避免覆盖用户整理字段

### 本地删除流

默认：

- 只删除本地关系

可选：

- 同时对 GitHub 执行 unstar

这条能力是显式用户选择，不是强绑定。

## 11. 失败模型

当前系统必须把外部失败当作常态处理，而不是异常边缘。

### 常见失败来源

- GitHub rate limit
- token 失效
- scope 不足
- 仓库 404
- 网络异常
- 部分同步失败

### 设计原则

- 尽量保留本地数据
- 不做静默破坏性操作
- 给前端返回足够清晰的结果或错误

### 典型例子

用户勾选：

- 本地删除
- 同时取消 GitHub Star

那么应该：

1. 先 GitHub unstar 成功
2. 再删除本地关系

否则会造成跨系统脏状态。

---

## 12. 前端架构备注

当前前端采用轻组件结构，而不是复杂状态管理框架，这在当前规模下是合理的。

当前主要界面区块：

- 侧边栏导航
- Hero / 同步控制区
- 统计卡
- 分页区
- 项目网格
- 项目详情抽屉
- 管理后台
- 更新记录抽屉

后续前端不应优先追求更复杂的框架，而应优先做：

- 信息层级优化
- 后台整理效率
- 分类与状态管理的可理解性

---

## 13. 安全与能力边界

### OAuth scope

原则是：

- 只申请当前功能真正需要的最小权限

例如：

- 登录与读取 Star
- 可选的取消 Star 能力

### 边界意识

系统当前代表用户执行的敏感动作主要有：

- 读取 Stars
- 检查 Star 状态
- 取消 Star

这些动作都应保持显式、可审计、可关闭。

---

## 14. 调度与未来自动化

长期建议支持：

- 高频手动增量同步
- 低频自动全量校验

推荐默认策略：

- 用户日常手动增量同步
- 每周自动全量重同步

这既平衡成本，也平衡正确性。

---

## 15. 安全扩展点

适合后续继续加的方向：

- 自动调度器
- 更强的规则分类系统
- 本地 NLP 分类器
- AI 批处理分类
- 导出能力
- 公开只读视图
- 更好的审计历史

需要谨慎对待的方向：

- 把它做成通用书签系统
- 合并 `Project` 和 `UserProject`
- 把核心同步逻辑搬到前端
- 让 AI 成为必需依赖
- 用一个粗暴的 `isManualEdited` 锁死整条记录

---

## 16. 当前最值得继续推进的内容

### 第一优先级

- 规则分类重构
- 分类来源与依据
- 手动分类保护
- 降低未分类项目比例

### 第二优先级

- 后台整理效率增强
- 搜索、排序、批量操作
- 未分类项目专门整理视图

### 第三优先级

- 自部署能力补强
- 更规范的配置与升级文档
- 测试与工程护栏

### 暂缓

- AI 全量介入
- 本地 NLP 分类器

---

## 17. 一句话架构总结

> GitHub Star Show 是一个“GitHub 负责远端事实、本地数据库负责用户整理结果”的混合同步系统，它把 GitHub Stars 转化成一个可长期维护的个人开源项目库，而不是一个一次性展示列表。
