# 功能规划与待做方案

这份文档记录当前 `GitHub Star Show` 尚未实现、但已有初步方案的功能项。

它与 `CURRENT_STATUS.md` 的区别是：

- `CURRENT_STATUS.md` 讲现在是什么状态、已知什么问题
- `ROADMAP.md` 讲接下来可以做什么、为什么做、怎么做

---

## 优先级标记

| 标记 | 含义 |
|------|------|
| P0 | 核心体验缺失，建议尽快做 |
| P1 | 显著提升日常使用效率 |
| P2 | 有价值但可延后 |
| P3 | 远期或需要外部条件 |

---

## 一、完善已有功能

### 1.1 分类规则管理界面（P0）✅ 已实现

**现状**：已实现。后台新增"分类规则管理"面板，支持 Topic/Keyword/Language 三种匹配类型。自定义规则通过 JSON 文件持久化存储，同步和重跑时优先于内置规则生效。内置规则作为 fallback 保留。

---

### 1.2 批量整理（未分类工作台增强）（P0）✅ 已实现

**现状**：已实现。未分类视图中每张卡片增加多选 checkbox，顶部出现批量操作栏，支持全选、批量归类到 X 分类、批量标记待研究。批量操作通过遍历 PATCH 逐个处理。

---

### 1.3 分类重跑保护（P1）

**现状**：重跑规则分类会覆盖所有项目的分类，包括用户手动整理的。当前 `categorySource` 字段记录了分类来源，但重跑逻辑没有区分对待。

**目标**：重跑时提供两种模式：
1. **仅处理未分类** — 跳过 `categorySource === 'manual'` 的项目
2. **全部重跑** — 但保留手动分类的备份或确认提示

**方案要点**：
- 后端接口增加 `mode` 参数：`uncategorized-only` / `force-all`
- `uncategorized-only` 模式下跳过 `categorySource === 'manual'` 的项目
- 前端按钮拆分为两个，或下拉选择模式

**价值**：避免用户丢失手工整理结果，建立信任感。

---

### 1.4 项目详情抽屉增强（P1）✅ 已实现

**现状**：已实现。抽屉增加"编辑"按钮，切换为编辑态后可编辑分类（下拉选择）、状态（下拉选择）、备注（textarea）、推荐标记（checkbox）。保存即时更新列表，不加载 AdminPanel。

---

## 二、全新功能

### 2.1 项目批量导入（P1）

**现状**：只支持单个 `owner/repo` 导入。

**目标**：支持从 GitHub Star 列表批量选取导入，或粘贴多个 URL 一次导入。

**方案要点**：
- 前端支持粘贴多行 URL / `owner/repo`
- 后端增加 `POST /api/projects/import-batch` 接收数组
- 去重逻辑：已存在的项目跳过
- 进度反馈：WebSocket 或轮询

---

### 2.2 数据导出（P1）

**现状**：用户的数据完全在 SQLite 中，没有导出机制。自托管用户尤其关心数据可移植性。

**目标**：导出项目库为 JSON / CSV。

**方案要点**：
- 后端增加 `GET /api/projects/export?format=json|csv`
- JSON 格式包含所有字段，适合备份和恢复
- CSV 格式适合 Excel 打开做进一步分析
- 导出按钮放在后台或用户设置区域

---

### 2.3 Star 趋势追踪（P2）

**现状**：每次同步没有记录项目的 star 数量变化，项目详情只显示当前 star 数。

**目标**：在同步时记录 `stargazers_count`，在项目详情页展示趋势图。

**方案要点**：
- 新增 `StarSnapshot` 或利用现有的 `SyncRun` 关联
- 每次同步写入当前 star 数 + 时间戳
- 前端使用 SVG 绘制趋势图（不需要 chart.js 等依赖）
- 保持轻量：纯 CSS + SVG，无第三方图表库

**价值**：GitHub 自身不提供 star 历史趋势，这是本项目的独特价值。

---

### 2.4 包管理器依赖探测（P2）

**现状**：项目详情里没有技术栈依赖信息。

**目标**：从 `package.json` / `requirements.txt` / `go.mod` / `Cargo.toml` 等文件提取依赖信息。

**方案要点**：
- 利用 GitHub API 获取仓库内容（已有 README 拉取的基础设施可复用）
- 提取关键依赖显示在项目详情中
- 标记已掌握的技术栈

**风险**：
- 额外的 GitHub API 调用，受速率限制
- 大型仓库的依赖文件可能很大

---

### 2.5 分类统计仪表盘（P2）

**现状**：首页 4 个 stat 卡片只显示总数（全部/推荐/待整理/远端异常）。

**目标**：扩展为更丰富的仪表盘：语言分布、分类占比、同步历史时间线。

**方案要点**：
- 后端聚合统计接口 `GET /api/projects/stats`
- 前端使用纯 SVG 绘制分布图
- 作为 stat 区域下方的可展开面板，不挤占主要空间

---

### 2.6 键盘快捷键（P2）

**现状**：所有操作依赖鼠标。

**目标**：为高频操作增加键盘快捷键。

**方案要点**：
- `s` / `Cmd+K` — 聚焦搜索框
- `1-7` — 切换分类导航
- `t` — 打开未分类视图
- `a` — 打开后台
- `Escape` — 关闭抽屉/下拉
- 使用 `onKeyDown` 监听，不要引入全局库

---

### 2.7 相关项目发现（P3）

**目标**：在项目详情中显示"收藏此项目的用户也收藏了..."。

**方案要点**：
- 简单版本：相同分类下的其他项目
- 进阶版本：分析用户收藏模式的协同过滤
- 进阶版本需要较多用户数据才有意义

---

### 2.8 多 GitHub 账号关联（P3）

**目标**：一个用户关联多个 GitHub 账号，统一管理多个账号的 Stars。

**方案要点**：
- User 与 GithubAccount 已是 1:N 关系
- 需要 UI 支持"添加另一个 GitHub 账号"
- 同步时合并多个账号的 Star 列表
- 需要处理跨账号去重

## 三、工程与运维

### 3.1 自部署文档 + Docker Compose（P1）

**现状**：`DEPLOYMENT.md` 已有基础说明，但没有 Docker Compose 编排，也没有升级/备份/回滚的完整流程。

**目标**：提供一套完整的自部署方案。

**方案要点**：
- Dockerfile：前端 Nginx 静态服务 + 后端 Node.js
- docker-compose.yml：前端 + 后端 + SQLite 数据卷
- 升级说明：拉取镜像 → 备份数据库 → 启动新版本 → 回滚步骤
- 备份脚本：定时备份 SQLite + .env

---

### 3.2 自动化定时同步（P1）

**现状**：同步必须手动触发。

**目标**：后端定时任务自动执行增量同步。

**方案要点**：
- 使用 node-cron 或 setInterval，不需要外部依赖
- 可配置同步间隔（默认 6 小时）
- 只在用户有活跃 session 时执行
- 同步记录写入 SyncRun

---

### 3.3 前端测试（P2）

**现状**：前端零测试。

**目标**：为核心组件补 smoke test。

**方案要点**：
- 使用 Vitest + @vue/test-utils
- 优先覆盖：EmptyState、ProjectGrid、SidebarPanel、AdminPanel
- 不追求高覆盖率，只保证关键渲染路径不挂

---

### 3.4 后端 API 文档（P2）

**现状**：API 没有文档，新开发者需要读路由代码。

**目标**：使用 JSDoc + 自动生成或手写 API 文档。

**方案要点**：
- 为每个路由添加 JSDoc 注释（method、path、params、response）
- 生成 Markdown 或使用 Swagger
- 覆盖所有 `/api/*` 端点

---

## 四、关于不做（明确排除）

这些功能被明确排除在当前产品定位之外：

- **AI 作为必需依赖** — AI 只做可选增强，不成为系统正常运行的必要组件
- **合并 Project 与 UserProject** — 两个模型各自承担不同职责
- **远端状态自动硬删除** — 远端取消 Star 不会自动删除本地记录
- **通用书签管理器** — 不管理非 GitHub 链接
- **社交功能** — 不关注、不评论、不协作
- **移动端优先** — 桌面端是主场景，移动端只保证可读
- **实时协作** — 没有 WebSocket 实时同步多人编辑
